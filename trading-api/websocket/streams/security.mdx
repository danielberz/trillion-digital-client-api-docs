---
title: "Security"
description: "Securities available to trade, with their increments and size limits."
---

Streams Trillion Digital's security master: the securities supported over the API
and available to trade. Subscribe to this first — it tells you what symbols exist
and, critically, the increments your orders must respect.

The first message carries a snapshot of every available security and is flagged
`initial: true`. Every message after that is a **delta** against that snapshot,
not a fresh copy of the security master.

## Subscribe

```json Client → server
{
  "reqid": 2,
  "type": "subscribe",
  "streams": [{ "name": "Security" }]
}
```

### Parameters

<ParamField body="Symbols" type="string[]">
  Optional list of symbols to filter the subscription on. Omit for all securities.
</ParamField>

<Warning>
Increments are the most common cause of rejected orders. A quantity or price that
is not a whole multiple of the relevant increment will be rejected. Note that
**which** increment applies depends on the currency you express the order in:
`MinSizeIncrement` for base-currency orders, `MinAmtIncrement` for quote-currency
orders. Round before submitting rather than reacting to a rejection.
</Warning>

## Maintaining a local security master

Merge each row into a local map keyed by `Symbol`: apply rows with
`UpdateAction: "Update"`, and delete the entry on `UpdateAction: "Remove"`.
`SecurityID` is informational and is not the merge key.

<Warning>
Rebuilding your security master from each message — rather than merging into the
snapshot — silently empties it. Only the first message is a full set; every later
message contains just the securities that changed, so a client that replaces its
map on each message ends up believing only one or two symbols are tradable and
rejects its own orders on everything else. Equally, a client that ignores
`UpdateAction` keeps quoting and sizing against securities that have been
withdrawn.
</Warning>

<Note>
Three fields are not shaped the way the field table above implies, and a strict
deserialiser will fail on them:

- `SecurityID` is documented as a string but is published as a JSON number
  (`"SecurityID": 2`). Parse it permissively; do not key anything off it.
- `SizeBuckets` is documented as an array of decimals but is published as an
  array of objects (`[{ "Size": "0" }]`).
- `Expiration` is documented as a decimal, not a datetime, despite being a point
  in time.

`SizeDisplaySpec` is also present on the wire — the counterpart to
`PriceDisplaySpec` — but is absent from the specification's field table, so
neither its optionality nor its full value set is defined. Treat it as display
metadata only.
</Note>
